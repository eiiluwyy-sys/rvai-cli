# P4.3B reproducible MobileNetV2 ONNX model pipeline

## Purpose

P4.3B defines an offline, reproducible production pipeline that converts the
identified MobileNetV2 FP32 ONNX model into a statically quantized INT8 ONNX
artifact and produces the evidence needed for later RVAI integration.

The pipeline covers:

1. source FP32 model identity and graph inspection;
2. calibration and evaluation dataset manifests;
3. ONNX Runtime static INT8 quantization;
4. FP32 and INT8 evaluation;
5. accuracy, model-size, and output-consistency comparison;
6. reproducibility and environment metadata; and
7. deterministic artifact packaging.

Integration of the resulting verified MobileNetV2 INT8 artifact into an RVAI
Manifest is a later, separately reviewed boundary.

## Non-goals

P4.3B does not add or change:

- llama.cpp, GGUF, Qwen, or chat inference;
- CUDA execution-provider product integration;
- ESWIN NPU compilation;
- model training or object detection;
- physical RISC-V benchmarking;
- `BenchmarkResult`, `RunRecord`, or result comparison behavior;
- builtin GEMM or its native and riscv64-QEMU execution paths; or
- the P4.3A `InferenceResult` schema or `rvai infer` behavior.

The presence of a GPU on an execution host does not change these boundaries.
The first production pipeline uses `CPUExecutionProvider` throughout.

## Repository and execution authority

The local checkout is the authoritative source tree. Remote hosts are
execution-only and must not contain independently edited source.

- Synchronize source with `~/bin/rvai-sync`.
- Run remote validation with `~/bin/rvai-remote-test`.
- Use `~/bin/rvai-remote-shell` only for necessary interactive inspection.
- Do not use SCP or arbitrary `rsync` commands.

Production models, generated artifacts, datasets, reports, and packages remain
outside Git. CI uses only tiny committed fixtures and performs no model or
dataset downloads.

## Frozen initial production configuration

The first production run uses exactly one quantization configuration. It does
not perform a parameter search.

```yaml
quantization:
  method: static
  format: qdq
  activation_type: quint8
  weight_type: qint8
  per_channel: true
  calibration_method: minmax
  execution_provider: CPUExecutionProvider
  calibration_order: manifest

calibration:
  pilot_samples: 200
  production_samples: 1000

evaluation:
  pilot_samples: 200
  production_samples: 5000

acceptance:
  max_top1_drop_percentage_points: 1.0
  max_top5_drop_percentage_points: 1.0
  min_model_size_reduction_ratio: 0.50
  min_top1_agreement_ratio: 0.95
  require_zero_inference_failures: true
  require_finite_outputs: true
```

Static quantization establishes the intended offline edge-deployment path. QDQ
keeps explicit `QuantizeLinear` and `DequantizeLinear` nodes for structural
inspection. QUInt8 activations, per-channel QInt8 weights, and MinMax
calibration form the first general MobileNetV2 baseline. Deterministic manifest
order and CPU execution remove avoidable provider and sampling variability.

Entropy, Percentile, QOperator, operator exclusions, or different activation
types may be considered only after the first frozen configuration has produced
and preserved a complete result. P4.3B does not search multiple configurations
in its first run.

The production evaluation target is 5,000 independently labelled samples. If
fewer than 5,000 suitable samples exist, the pipeline must use the complete
available independent labelled set and record the actual sample count. It must
not silently reuse calibration samples to reach the target.

The acceptance thresholds are engineering objectives, not a promise that the
first production run will pass. A failed run remains immutable evidence. Any
later threshold or quantization change requires an explicit configuration
revision and a new report; an existing report must never be edited into a pass.

## Reviewed quantization configuration v2

After preserving the rejected `p43b-v1` production evidence, the reviewed v2
configuration is stored in `model-pipeline/mobilenet-v2-v2`. It keeps the
source model, preprocessing, sample counts, QDQ representation, data types,
per-channel weights, provider, deterministic order, and every acceptance gate
unchanged. Its only production changes are explicit Percentile calibration at
`99.999` and exclusion of `Conv_88`, `Conv_94`, and `Conv_95` from static
quantization.

Histogram calibration is explicitly chunked in manifest order with
`calibration_chunk_size: 50`. ONNX Runtime's Percentile calibrator otherwise
retains every exposed intermediate activation until the complete reader is
exhausted, which can exceed the memory available on a 16 GB development host
at 1,000 images. The chunk size is required to divide both the pilot and
production sample counts; each chunk updates the same histogram collector and
then releases its intermediate arrays before the next chunk. A fixed 200-image
check measured approximately 3.8 GiB peak RSS and zero swap for the 50-image
setting on the development host. The chunk size is part of the quantization
identity because incremental histogram merging can change the resulting
ranges; it is not a transparent runtime-only knob.

The exclusions were selected only after an ONNX Runtime QDQ activation-SNR
analysis and real-data screening on a fixed manifest prefix. `Add_89`,
`Conv_88`, and `Conv_94` showed the largest accumulated cross-model error;
the activation following `Conv_95` was also among the most sensitive. A fixed
200-image calibration and 500-image evaluation screen compared MinMax,
Entropy, Percentile, late-node exclusions, and final-Gemm output exclusion.
Final-Gemm output exclusion and Clip-only exclusions were rejected because
they did not improve the paired result. The selected candidate passed the
accuracy and size gates in that screen and improved Top-1 agreement relative
to the explicit MinMax v2 control, but the screen itself is not production
verification.

The v2 schema requires an explicit calibration method, optional Percentile
value, complete operator-type allow-list, exact node exclusions, and explicit
output-quantization exclusions. This prevents ONNX Runtime registry defaults
from silently changing the reviewed configuration. The v1 record shape is
retained as a separate schema branch so existing v1 evidence remains canonical
and independently verifiable.

## Reviewed acceptance configuration v3

The reviewed v3 configuration is stored in
`model-pipeline/mobilenet-v2-v3`. It retains the complete v2 quantization
configuration and changes only the acceptance policy. The v2 quantization
revision remains explicit in the file so an acceptance review cannot be
mistaken for a newly verified model artifact.

```yaml
acceptance:
  revision: v3
  max_top1_drop_percentage_points: 1.0
  max_top5_drop_percentage_points: 1.0
  min_model_size_reduction_ratio: 0.50
  min_top1_agreement_ratio: 0.90
  max_correct_to_wrong_regression_ratio: 0.03
  min_mean_top5_overlap_ratio: 0.85
  require_zero_inference_failures: true
  require_finite_outputs: true
```

The 90% Top-1 agreement gate is a reviewed project engineering threshold for
this non-safety-critical classifier, not a universal statistical standard. It
is paired with accuracy and regression gates so a candidate cannot pass merely
by producing similar but less correct predictions. Correct-to-wrong regression
counts samples for which FP32 Top-1 matches the independent label but INT8
Top-1 does not, divided by the complete evaluation sample count. Mean Top-5
overlap is the total intersection size of paired FP32 and INT8 Top-5 class sets,
divided by five times the evaluation sample count.

Retrospective evaluation of the preserved 5,000-image v2 evidence under these
new gates gives 89.32% Top-1 agreement, 2.46% correct-to-wrong regression, and
87.86% mean Top-5 overlap. The last two gates pass, but agreement remains 34
samples below 90%; changing the acceptance policy therefore does not turn the
preserved v2 run into an accepted v3 result.

A bounded-memory v3 screen used the fixed first 200 calibration images and
first 500 evaluation images. It varied histogram chunk size and the reviewed
sensitive-node exclusions while holding source, preprocessing, Percentile
value, provider, and sample order fixed:

| Candidate | Top-1 agreement | Top-1 drop | Correct-to-wrong | Top-5 overlap | v3 result |
|---|---:|---:|---:|---:|:---:|
| v2 baseline, chunk 50 | 90.6% | 0.4 pp | 2.0% | 87.56% | PASS |
| replace `Conv_95` exclusion with `Conv_82` | 92.6% | 2.0 pp | 3.0% | 87.64% | FAIL |
| additionally exclude `Conv_82` | 92.8% | 2.4 pp | 3.0% | 87.88% | FAIL |
| v2 exclusions, chunk 40 | 91.8% | 2.2 pp | 2.4% | 88.28% | FAIL |
| v2 exclusions, chunk 25 | 91.6% | 1.4 pp | 2.4% | 87.80% | FAIL |

The alternatives improved pilot agreement by at least four of 500 samples,
which is large enough to investigate the 34-of-5,000 production gap, but every
one exceeded the 1.0 percentage-point Top-1 degradation limit. None is adopted.
The v3 formal candidate therefore keeps the v2 chunk-50 quantization settings.

The subsequent complete production run used 1,000 calibration images and 5,000
independently labelled evaluation images. It reproduced INT8 artifact SHA-256
`65d5c5b548253352d192850631cf5fb04e0dbf6bb4370ad16235106b0518a2c5` and
passed seven of eight v3 gates. Top-1 agreement was 4,466 of 5,000 samples
(89.32%), below the 90.00% gate by 34 samples, so the immutable formal result is
`rejected`. The verified evidence package has content SHA-256
`5d358a9dc0f7fc536972130ca9d1a25957a87afd90307e2725092f1c2e93c6fc`.
P4.3C activation remains blocked until a separately reviewed quantization
revision produces an accepted new formal run.

## Frozen FP32 source identity

The production source configuration records this identity without placing the
model binary in Git:

```yaml
model:
  name: mobilenetv2-12
  format: onnx
  precision: fp32
  filename: mobilenetv2-12.onnx
  size_bytes: 13964571
  sha256: c0c3f76d93fa3fd6580652a45618618a220fced18babf65774ed169de0432ad5
```

Before calibration, inspection must record:

- SHA-256 and byte size;
- ONNX IR version and opset imports;
- producer name and producer version;
- every graph input and output name, element type, and shape;
- node and initializer counts;
- operator-type counts;
- ONNX checker status; and
- expected MobileNetV2 contract-match status.

Any source identity, checker, or expected-contract mismatch stops the pipeline
before calibration.

The frozen source artifact declares a symbolic `batch_size` dimension on both
its input and output. The graph contract therefore accepts either literal batch
dimension `1` on both tensors or the same non-empty symbolic batch dimension on
both tensors. Calibration, pseudo-labelling, FP32 evaluation, and INT8
evaluation still always supply an actual batch of one; arbitrary batching is
not introduced by P4.3B.

## Dataset manifests

Calibration and evaluation data are external inputs described by strict,
versioned manifests. A manifest records dataset name, version, split,
provenance, license, preprocessing identity, stable sample identifiers,
relative paths, labels, optional file digests, and deterministic sample order.

Absolute paths and image contents are not part of committed manifests.
Execution supplies an external dataset root. Resolved paths must remain under
that root, and optional sample digests must be verified before use.

Calibration and evaluation sets must be independently labelled. Duplicate
sample identifiers, duplicate paths, path traversal, invalid labels, missing
files, and undeclared overlap are validation errors. Manifest identity and the
actual selected sample count are included in every downstream record.

## Shared preprocessing contract

FP32 inspection, calibration, and FP32/INT8 evaluation use the existing P4.3A
MobileNetV2 preprocessing contract: RGB decoding, shorter-side resize to 256,
224 by 224 center crop, NCHW FP32 layout, pixel scaling, and ImageNet channel
normalization.

Implementation should reuse the existing preprocessing logic so calibration
and evaluation cannot drift from `rvai infer`. Such reuse must not alter the
P4.3A public schema, command, provider, or output behavior.

## Pipeline stages

### 1. Validate configuration and identities

Load strict pipeline, source-model, calibration-manifest, and
evaluation-manifest schemas. Calculate canonical configuration and manifest
digests. Reject incomplete, unsupported, or inconsistent inputs.

### 2. Inspect the FP32 source

Verify the frozen file identity, run the ONNX checker, inspect the graph, and
validate the declared MobileNetV2 input/output contract. No later stage may run
when inspection fails.

### 3. Validate and select data

Resolve samples against external roots, verify declared file identities, check
labels and set independence, and select the first requested number of samples
in manifest order. Record both requested and actual counts.

### 4. Calibrate and quantize

Feed the selected calibration samples to ONNX Runtime in manifest order using
the frozen preprocessing and quantization configuration. Produce an INT8 ONNX
model in a generated work directory. Inspect the result for the expected QDQ
structure and record its SHA-256 and byte size.

The frozen source model uses ai.onnx opset 12, while standard per-channel QDQ
requires the `axis` attribute introduced for `QuantizeLinear` and
`DequantizeLinear` in opset 13. The pipeline therefore converts a verified
in-memory copy to opset 13 with the ONNX version converter, checks the converted
copy, and records both opset versions before quantization. The frozen source
file is never modified, replaced, or re-identified by this compatibility step.

### 5. Evaluate FP32 and INT8

Run both models with `CPUExecutionProvider` over the same independently labelled
evaluation selection. Record Top-1 and Top-5 accuracy, per-sample prediction
data required for comparison, inference failures, non-finite outputs, and the
actual evaluated count. Timing is diagnostic only and is not a physical-device
or representative performance benchmark.

### 6. Compare and decide

Calculate FP32-to-INT8 Top-1 and Top-5 degradation in percentage points, model
size reduction, Top-1 agreement, and configured output-consistency metrics.
Evaluate every frozen acceptance gate independently and preserve all raw inputs
to the decision.

### 7. Capture reproducibility metadata

Record source, configuration, preprocessing, dataset-manifest, generated-model,
and report digests together with Python, ONNX, ONNX Runtime, NumPy, Pillow,
provider, platform, architecture, CPU, pipeline-schema, and local Git revision
information.

Timestamps and host-specific paths are informational run-envelope fields. They
must not change deterministic record identities.

### 8. Package artifacts

Create a deterministic package containing the generated INT8 ONNX artifact,
artifact checksum record, source inspection, configuration identity,
dataset-manifest identities, quantization report, FP32 and INT8 evaluation
summaries, comparison decision, and reproducibility metadata.

The package does not contain datasets. It does not contain the source FP32
model unless a later policy explicitly authorizes that inclusion.

## Failure and evidence policy

Each stage fails closed on invalid identity, schema, path, graph contract,
inference output, or package content. Failed production runs retain their raw
records and logs. A later rerun writes a distinct result and must identify the
configuration revision that motivated it.

Zero inference failures and finite outputs are mandatory acceptance conditions.
Accuracy, agreement, and size failures do not authorize automatic fallback to
another quantization configuration.

## Dependency boundary

The base RVAI installation remains independent of ONNX model-production
packages. Pipeline dependencies will be introduced later through a dedicated
optional installation extra and imported only by production tooling. This
document-only boundary does not change `pyproject.toml`.

## Validation policy

Automated validation uses a tiny, locally committed quantizable ONNX graph and
tiny local images. It must exercise schema validation, source inspection,
manifest safety, static QDQ quantization, FP32/INT8 evaluation, comparison, and
package verification without network access.

Production validation uses pre-provisioned model and dataset inputs on the
execution host. The approved remote workflow may run the full test suite,
inspect the formal FP32 source, validate manifests, perform CPU static
quantization, evaluate FP32 and INT8, package results, and capture environment
metadata. The remote host remains execution-only.

A repeat run with the same inputs and declared environment must reproduce the
INT8 model digest and all deterministic report content. Environment differences
must be recorded rather than hidden.

### Synthetic consistency pilot

When independently labelled ImageNet-compatible data is unavailable, the
non-public `scripts/run_p43b_synthetic_pilot.py` entry point may exercise B1
through B3 with deterministic procedural PPM images. It generates disjoint
calibration and evaluation candidates, assigns evaluation labels from the
frozen FP32 model's Top-1 predictions, performs static QDQ quantization, runs
paired FP32/INT8 evaluation, and writes canonical evidence records.

This is a proxy engineering check only. Its report is always `provisional`,
sets `production_verified` to false, identifies `fp32-top1-pseudo-label` as the
label source, and records limitations explicitly. Proxy accuracy must not be
presented as ground-truth ImageNet accuracy, production verification, or a
physical RISC-V benchmark. Generated images, models, and reports remain outside
Git. A verified production artifact still requires suitable independently
labelled external evaluation data.

Run the default 200/200 proxy pilot only against a pre-provisioned source model
whose filename, size, and SHA-256 match the frozen identity:

```bash
python scripts/run_p43b_synthetic_pilot.py \
  --model /external/models/mobilenetv2-12.onnx \
  --output /external/runs/p43b-synthetic-pilot-v1
```

The output directory must not already exist. The runner never downloads a
model or dataset and never replaces an existing model, manifest, or report.

### Deterministic proxy evidence report and package

B4.2 consumes an already completed B4.1 synthetic Pilot directory. It does not
regenerate data, rerun quantization, or evaluate either model. All JSON inputs
are reloaded through their strict schemas, required to be canonical, and
checked as one cross-record digest graph before any report or package is
created.

The generated `comparison.md` is deterministic and prominently identifies the
result as provisional FP32 Top-1 pseudo-label evidence. It reports every frozen
acceptance gate, including failures, and states that proxy accuracy is not
independently labelled ImageNet accuracy or production verification. It is not
a physical RISC-V performance report.

The directory package contains exactly the generated comparison report, the
INT8 ONNX artifact, and the 17 canonical B4.1 records. It excludes source FP32
models, images, dataset content, timestamps, logs, and host paths. Its payload
entries are sorted by canonical POSIX path. `content_sha256` hashes only the
canonical ordered entry array; `package-manifest.json` and `sha256sums.txt` are
not entries and therefore cannot recursively hash themselves.

Both the recorded run revision and current packager revision must identify
clean Git worktrees, including untracked-file detection. Construction uses a
hidden same-parent staging directory, verifies the complete staged package,
and publishes with Linux atomic no-replace directory rename semantics. An
existing destination is never overwritten, and an incomplete staging directory
is removed after failure.

The non-public packaging tool has explicit build and verification modes:

```bash
python scripts/package_p43b_evidence.py build \
  --run /external/runs/p43b-synthetic-pilot-v1 \
  --output /external/packages/p43b-synthetic-evidence-v1 \
  --repository /path/to/clean/rvai-cli

python scripts/package_p43b_evidence.py verify \
  --package /external/packages/p43b-synthetic-evidence-v1
```

Verification is read-only and independent of the builder. It rejects missing,
additional, modified, symlinked, or non-regular files; invalid schemas or
digest links; a changed INT8 artifact; a non-canonical Manifest; or checksum
and content-digest disagreement.

## Formal production runner and package

The formal runner consumes pre-provisioned calibration data and independently
labelled evaluation data. It never downloads models or datasets. The Git tree
must be clean at both the start and end of the run, the output directory must
not exist, and every input dataset is revalidated after evaluation to detect
changes during a long run.

For a reviewed ImageFolder whose class directories are named `0` through
`999`, the preparation tool deterministically selects the lexicographically
first image in each class for calibration and the next five for evaluation.
It decodes every image, records every SHA-256 digest, verifies zero cross-split
content overlap, and refuses unexpected files, symlinks, missing classes, or an
existing output directory:

```bash
python scripts/prepare_p43b_imagefolder.py \
  --root /external/datasets/imagenetv2-matched-frequency-format-val \
  --output /external/manifests/imagenetv2-p43b-v1 \
  --dataset-name imagenetv2-matched-frequency \
  --dataset-version b-33 \
  --provenance "ImageNetV2 MatchedFrequency b-33; independently labelled" \
  --license "Flickr per-image terms; reviewed external research dataset"
```

The tool does not grant dataset rights or infer provenance. The operator must
review and supply accurate provenance and license text before treating the
result as formal input.

```bash
python scripts/run_p43b_production.py \
  --model /external/models/mobilenetv2-12.onnx \
  --config model-pipeline/mobilenet-v2 \
  --calibration-manifest /external/manifests/imagenetv2-p43b-v1/calibration-manifest.yaml \
  --calibration-root /external/datasets/imagenetv2-matched-frequency-format-val \
  --evaluation-manifest /external/manifests/imagenetv2-p43b-v1/evaluation-manifest.yaml \
  --evaluation-root /external/datasets/imagenetv2-matched-frequency-format-val \
  --output /external/runs/p43b-production-v1 \
  --repository "$PWD"
```

Calibration requires the configured 1,000 samples. Evaluation targets 5,000
samples and records use of the complete independently labelled set when fewer
are available. A completed run is `accepted` or `rejected`; both outcomes are
immutable evidence. An operational failure writes `records/failure.json` and
retains every canonical record completed before the failure.

Build and independently verify the deterministic formal package with:

```bash
python scripts/package_p43b_production.py build \
  --run /external/runs/p43b-production-v1 \
  --output /external/packages/p43b-production-v1 \
  --repository "$PWD"

python scripts/package_p43b_production.py verify \
  --package /external/packages/p43b-production-v1
```

The formal package includes the INT8 artifact, canonical input identities,
validation records, evaluations, comparison, report, reproducibility record,
and checksums. It excludes the source FP32 model, images, and dataset roots.

## Deferred RVAI integration

P4.3B produces an INT8 model and supporting evidence. It does not modify the
existing dormant `mobilenet-int8` Manifest or make INT8 inference available
through `rvai infer`.

A later integration change must independently review the packaged artifact
location, SHA-256, size, license, provenance, preprocessing and output
contracts, ONNX Runtime compatibility, and inference results before updating
the Manifest or runtime adapter.
